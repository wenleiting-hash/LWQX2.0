
# 《老温轻省》全栈架构与系统设计白皮书 (V2.0 高性能版)

>**文档定位**：本文件为《老温轻省》（原代号：极省惠选/老温铺子）项目的核心架构蓝图。后续所有代码生成、模块开发及测试验证，均需以此文档为最高准则。

## 一、 系统全景与架构选型 (Architecture Overview)

本项目采用 **AI-Native + Serverless (无服务器)** 的分布式架构，彻底抛弃传统的自建服务器模式，以实现“极简启动、按需扩容、零边际运维成本”的战略目标。
### 1.1 架构分层拓扑

- **展示层 (前端小程序)**：基于微信原生 **WeUI 组件库**，保障包体积控制在 2MB 以内，实现冷启动秒开。禁止前端直接连通第三方聚合平台。
- **计算引擎层 (Serverless 云函数)**：作为核心“大脑”，负责 API 代理、归因参数注入与“现金转积分”的汇率清洗。
- **数据底座层 (云开发 JSON 数据库)**：采用非关系型（NoSQL）文档数据库。实现高频数据（商品缓存）的 TTL 自动销毁与核心资产（积分）的事务级强一致性。
- **管理与业务闭环层**：采用微信云开发自带的 **CMS 内容管理系统**作为全局风控驾驶舱。业务闭环（实物发货/变现）100% 寄生于官方免费的【微信小店】。

## 二、 核心合规基线与风控规则 (Compliance & Risk)

本项目涉及财务类转化，以下三条底线属于**“一票否决的研发禁区”**：
1. **【资金红线】严禁现金体系**：全端代码（含变量命名、UI 呈现）彻底封杀“返现、返利、佣金”等敏感词。必须通过中间件 `formatMoneyToPoints` 将官方佣金 1:1 或按设定汇率转化为“系统积分”进行展示。
2. **【合规红线】严禁提现与资金池**：坚决不开发提现功能，不设绑定银行卡入口。积分单向流入微信小店进行权益兑换，彻底切断“二清”风险。
3. **【隐私红线】极简静默授权**：全程无弹窗，不索要手机号、真实姓名和收货地址。通过 `wx.login` 静默获取 `OpenID` 作为用户唯一身份标识。

## 三、 系统契约与 API 设计规范 (System Contracts)

前后端交互必须遵循统一的 DTO (Data Transfer Object) 标准。以下为核心业务流的数据契约：
### 3.1 核心节点 1：`parse_and_convert` (查券与资产清洗引擎)

- **触发时机**：前端 `onShow` 嗅探到剪贴板包含电商链接时触发。
- **Request DTO (前端传入)**：
	TypeScript
	```
	interface ParseRequest {
	  query: string;       // 剪贴板提取的原始文本/链接
	  user_openid: string; // 归因所需的用户唯一标识
	}
	```
- **Response DTO (后端返回)**：
	TypeScript
	```
	interface ParseResponse {
	  success: boolean;
	  msg?: string;        // 错误信息（如：该商品暂无专属优惠）
	  data?: {
	    title: string;     // 商品名称
	    pic: string;       // 商品主图 URL
	    origin_price: number;
	    coupon_price: number;
	    points_display: string; // 已清洗的安全文案，如："预估可得 15 积分"
	    jump_url: string;  // 带有平台 PID 与 source=search&openid=xxx 归因参数的跳转链接
	  }
	}
	```

### 3.2 核心节点 2：`get_ttl_feed` (种草瀑布流获取)

- **触发时机**：用户进入“发现”页时触发。
- **架构约束**：严禁在此节点直连外部 API。必须读取云数据库 `ttl_feeds` 的内部缓存数据，实现成本熔断。

## 四、 核心数据模型与 DDL (Data Dictionary)

数据库设计严格遵循**读写分离、高频查询索引化、资产操作原子化**的原则。
### 4.1 实体 1：`users` (用户资产表)

- **主键**：`_id` = `openid`。
- **架构约束**：更新 `points_balance` 必须使用 `db.command.inc` 原子操作。

JSON
```
{
  "_id": "oX_xxxxxxxxx", 
  "points_balance": 1250,      // 当前可用积分 
  "points_frozen": 300,        // 冷冻中积分 (防退款机制)
  "total_earned": 5000,        // 历史累计赚取积分 
  "version": 1,                // 乐观锁版本号
  "status": "active",          // 账户状态: active / frozen
  "created_at": "timestamp"
}
```
### 4.2 实体 2：`orders` (订单归因对账表)

- **主键**：`_id` = 内部生成 UUID。
- **索引**：`order_sn` (外部订单号，唯一索引)；`(openid, status)` (复合索引)。

JSON
```
{
  "_id": "uuid",
  "order_sn": "3829472394723", 
  "idempotent_key": "sn_status_idx", // 幂等键防重发
  "openid": "oX_xxxxxxxxx",    
  "source": { "channel": "search" }, // 归因来源: search/feed
  "financial": {
    "points_expect": 10.5      // 预估发放积分数额
  },
  "status": 1,                 // 1:待结算(下单), 2:已入账(结算), 4:已失效(退款)
  "create_time": "timestamp"   
}
```
### 4.3 实体 3：`point_logs` (金融级流水审计表)

- **约束**：只允许 `INSERT`，绝对禁止 `UPDATE` 或 `DELETE`。

JSON
```
{
  "_id": "log_id",
  "openid": "oX_xxxxxxxxx",
  "type": "ORDER_REWARD",      // 类型: ORDER_REWARD / STORE_REDEEM / REFUND_REVOKE
  "amount": 10.5,              // 变动额 (支持正负)
  "balance_snapshot": 1260.5,  // 变动后的余额快照
  "ref_id": "3829472394723",   // 关联业务单号
  "created_at": "timestamp"
}
```
### 4.4 实体 4：`ttl_feeds` (瀑布流商品缓存表)

- **机制**：必须配置 `expireAt` 字段的 TTL 索引，48小时后自动物理清理。

JSON
```
{
  "_id": "product_id",
  "platform": "tb",
  "coupon_url": "...",
  "points_reward": 50,
  "expireAt": "Date Object",   // TTL 自动销毁触发点
  "category_tag": "dorm_99"    // 业务分类标签
}
```

## 五、 非功能性指标与性能压测基线 (NFRs)

为保障极致的用户体验，系统需满足以下工程级指标：

|**性能指标**|**达标阈值**|**架构师落地解决方案**|
|:-:|:-:|:-:|
|**FCP (首次内容绘制)**|**< 0.8s**|强制采用原生 WeUI；静态资源 (Tab 图标等) 放入本地包；开启 `app.json` 的按需注入。|
|**API 响应耗时**|**< 200ms**|针对 `get_ttl_feed`，直接走云数据库缓存。云函数开启“预留并发实例”消除冷启动延迟。|
|**高并发可用性 (QPS)**|**单节点 > 5000**|针对双十一等订单回调洪峰，订单入账逻辑必须采用**云消息队列异步解耦**，防止数据库锁表冲突。|
|**数据一致性**|**100% 幂等**|积分发放入账接口，必须依赖 `point_logs.ref_id` 进行唯一性校验。支持异常情况下的无副作用重试。|

## 六、 部署架构与 DevOps

1. **沙盒与生产环境隔离**：必须建立两套云开发环境（如 `lwqs-dev` 与 `lwqs-prod`）。所有 DDL 变更需先在 dev 环境验证。
2. **API 密钥管理**：折淘客 `AppKey` 等第三方机密数据，严禁硬编码至 `index.js`，必须依托腾讯云函数的**环境变量 (Environment Variables)** 进行下发。
3. **零代码后台**：后台系统直接复用云开发的 **CMS 扩展能力**，关联 `users` 与 `orders` 集合，仅开放给唯一的超级管理员使用，不做复杂的 RBAC 角色权限模型。
